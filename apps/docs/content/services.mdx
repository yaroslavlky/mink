# Own the services you start

Mark a command as `run.mode: service`. A service stays attached to the current Mink session. It becomes ready after the configured probe, then continues while subsequent workflow steps run.

```yaml
kind: command
name: Development server
command: node server.mjs
run:
  mode: service
  startup_timeout_ms: 10000
  ready:
    type: http
    url: http://127.0.0.1:3000/health
    interval_ms: 100
```

| Probe               | Readiness rule                                                          |
| ------------------- | ----------------------------------------------------------------------- |
| `process` (default) | Shell process spawned; application initialization is not verified       |
| `tcp`               | Connection succeeds to `host` (default `127.0.0.1`) and required `port` |
| `http`              | GET to required HTTP(S) `url` returns a 2xx response; redirects fail    |
| `command`           | The configured command exits successfully                               |
| `log`               | Output contains `log_line`; `ready_log_line` is shorthand               |
| `file`              | The configured file exists                                              |

HTTP and TCP attempts have a short bounded timeout. Failed attempts repeat at `interval_ms` (default 100). Startup defaults to 30 seconds; expiration stops the process tree and produces a failed, timed-out result. Health addresses are literal configuration values; they are not derived from parameterized ports.

## Manage a session

Press **Ctrl+S** in the palette to inspect owned services and their recent output. Stop sends SIGTERM followed by SIGKILL if necessary; kill sends SIGKILL immediately. Restart stops the old instance and launches the same prepared service inputs. It does not rerun its one-shot prerequisites. Open uses the explicitly configured HTTP health URL and only allows HTTP(S).

Mink rejects a second scheduled/running instance of the same service ID, including concurrent requests while the first is waiting on dependencies. Stopped or failed services can be started again.

## Shutdown

On Linux/macOS each child starts in its own POSIX process group. On Windows a supervisor assigns a suspended process to a kill-on-close Job Object before allowing it to create descendants. Cancel, timeout, shutdown, and natural shell exit clean up its descendants. SIGTERM escalates to SIGKILL after 800 ms if the shell has not exited. Mink acts only on process groups it created.

Use `mink run <service> -D` to hand a service to the per-project background supervisor. `mink attach` shows its status; `mink detach` disconnects without stopping it, and `mink stop --all` performs an explicit shutdown. The transport is a permission-restricted Unix socket or Windows named pipe. `mink scale`, `mink disable`, `mink logs`, `mink events`, and `mink runs` use the same protocol, so closing the TUI does not stop supervised services. Foreground sessions are still disposed when their client exits. A child that deliberately detaches into a new process group is beyond Mink ownership.

Scheduled commands accept `schedule.interval_ms` or the minimal cron form `*/N * * * *`. Disabled services do not start until enabled. `replicas` declares the initial service count, and `mink scale <id> <count>` changes it at runtime.

## Continuous health and bounded restart

```yaml
run:
  mode: service
  ready: { type: http, url: 'http://127.0.0.1:3000/health' }
  health:
    type: http
    url: http://127.0.0.1:3000/health
    interval_ms: 1000
    failure_threshold: 3
  restart:
    max_attempts: 2
    delay_ms: 500
    backoff: 2
```

`ready` checks startup. Optional `health` continues TCP or HTTP checks after readiness.
Without `restart`, an unhealthy service stays running, appears as unhealthy, and can
recover when probes succeed. With `restart`, reaching the failure threshold stops
the owned process tree and starts a replacement. Non-zero service exits can also
trigger restart. `max_attempts` counts replacements after the initial attempt, from
0 to 10; backoff is capped at 60 seconds. Stop/cancellation never triggers restart.

The logical service retains a single completion promise across replacements and
only one owned instance. Restart startup reacquires a root process slot. Exhausting
the budget reports failure to the CLI. One-shot prerequisites are not repeated.
